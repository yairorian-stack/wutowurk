# 運用・次の開発段階

## 現在の状態

Google認証・事前登録アドレス制限・アカウント管理と登録DBの権限制御を実装済み。Supabaseプロジェクトは所有者が作成済み。Google OAuth・追加DB設定・Next.js公開先は未接続で、実ログインは未稼働。GitHub Pagesはログイン準備画面だけに変更し、社内画面を開けない。接続・初期管理者確認・運用手順は `docs/AUTH_SETUP.md`。

業務データの共有DB化、PDFアップロード、資料承認は未実装。次のサンプル操作手順は、認証接続後の試作品、またはループバック内の架空プロトタイプを対象とする。

## 日々の記録・月次目標の試用

`売上・日報`を開くと、データが接続されていない場合は「ポータル未反映」と表示する。元シートが未集計という意味ではない。試用する場合は「サンプルで操作を試す」を選び、店舗と月を選ぶ。「月次目標を設定」で月間売上と人時売上高の2項目を設定する。前月の設定がある場合はコピーできる。日報に売上・全員の総労働時間・メモを入力し、その日の仕入れ・支払い等も必要に応じて追加する。1回の保存で出納帳と月次進捗へ反映する。入力後は現金残高、残り売上、目標比率を確認する。サンプル専用のため、実際の経営数値は入力しない。「サンプルを閉じる」でデータの反映状況へ戻る。

提供された月累計を先に表示する場合は、基準日と出典を付け、日別取込・残高照合とは分ける。実額の公開承認がない場合、非公開の確認用HTMLだけをリポジトリ外へ作成する。公開サイトは閉じたログイン準備画面のみ。開発用の権限プレビューを認証として使わない。

入力を訂正する場合は同じ日の日報を開く。既存の現金明細も編集でき、二重登録しない。登録済み明細の取消は出納帳から理由を記録して行う。目標の編集履歴は「記録の変更履歴」で確認する。全社集計では両店舗の月次目標を設定する。

## 週次の試用手順

1. ホームで本店の今週の3件と33%の達成率を確認。
2. 週次アクションを開き、次週に移動。「先週から複製」を実行し、全件が未着手として引き継がれることを確認。
3. 複製をもう一度実行し、二重登録が拒否されることを確認。
4. 816を選び、今週の未完了の目標を翌週に繰り越す。元の週に戻って、記録が残ることを確認。
5. 目標の詳細から編集し、成果・振り返り・次週の課題を記入。再読み込み後、検索と変更履歴で確認。
6. 設定で一般スタッフ・店舗管理者に切り替え、自店舗以外や編集操作が表示されないことを確認（UIプレビューのみ）。

## STEP 3 で確認する判断

自己評価シートの第1案は「自己評価」から試用できる。入力は画面内だけで保持し、ページ移動前にコピーまたは印刷する。接客・部門リーダーの項目は検討案。氏名・評価・振り返りは既存のブラウザー保存データに混在させない。個人ログイン・非公開DB導入前に共有評価台帳として運用しない。詳細手順は `docs/SELF_EVALUATION.md`。

シフトは「シフト」画面で共通CSVを読み込むと可視化できる。勤務データは画面内だけに保持し、離脱で消える。Airシフトのリンクは自動同期ではない。自動取得の公式連携方式・アカウント接続・非公開保存先が確認できるまでは「未接続」とする。

本店の紙シフトは直接入力できる。画面を離れる前にCSVで控えを保存する。「本店ゴミ出し」は18番地区の照合用日程を表示し、実際の自動通知と区別する。GAS追加コードは `automation/garbage/README.md` の手順に従い、既存LINEテストを維持して、公式PDFとの照合・実着信・時刻精度の検証後にのみ稼働する。

提供売上JSONは日報画面の専用欄から取り込む。空欄・基準日・日別合計と月累計を検証する。「この端末に保存」で専用ブラウザー記録へ保存し、先にバックアップする。サンプルや現金出納帳へは混在させない。端末間共有・サーバー権限管理はない。実額を公開HTMLへ組み込むには依頼者の明確な承認が必要。詳細は `docs/SHIFTS_AND_IMPORTED_SALES.md`。

依頼者と認証・保存の提供元、予算、運用責任者を確認してから本番向けに接続する。Supabase / PostgreSQL と Vercel は候補であり、契約済みではない。公開や有料契約は依頼者の明示承認後に実施する。

- 初期管理者の登録手段と本人確認。招待を基本にし、誰でも管理者登録できる経路は設けない。
- 所属店舗・役職名・システム権限の確定、変更できる管理者の範囲。
- 個人情報の保存地域・利用目的・保持期間、退職時の停止・削除方針。
- 認証メールの送信元、ドメイン、HTTPS、セッションの有効期間。
- 承認済み就業規則PDFの原本・版・公開対象。未承認資料を一般スタッフ向けAPIに返さない。
- 認証セッションと許可をサーバーで検証し、DB側の店舗制約も併用する。権限をローカルストレージから取得しない。
- 変更履歴はサーバー側で追記し、一般ユーザーによる書き換え・削除を禁止する。

認証キー・管理用キーをコード・チャット・クライアント公開変数に置かない。必要な値は環境設定で管理する。試作品のローカル保存データを本番へ自動移行しない。

## STEP 4 の必須セキュリティテスト

- 未認証のAPIリクエストは拒否。
- 一般スタッフは所属店の目標だけ閲覧でき、作成・更新できない。
- 店舗管理者は自店舗だけ編集でき、他店IDを直接指定しても読み書きできない。
- 全社管理者の操作範囲と、システム権限変更の許可範囲が設計どおりである。
- ロールや所属店のリクエスト改ざん、退職済みユーザーのセッション、未承認PDFの直接取得を拒否。
- 同時登録でも目標が週3件を超えず、同時更新は競合として扱う。
- 入力検証、監査履歴、署名URLの期限、モバイルフォーム、キーボード操作を検証。

現段階の単体・E2Eテストは上記のサーバー安全性を保証しない。

## STEP 5 の公開準備

初期管理者を安全に招待し、依頼者が本人のログインを確認。承認済み資料を登録。プライバシーと社内利用ルール、問い合わせ先を用意し、2店舗の管理者に操作説明を行う。依頼者の公開承認後にのみドメイン・公開環境を設定する。

DBと資料ストレージを別々にバックアップ。日次・保持30日、RPO 24時間 / RTO 1営業日は合意前のたたき台。バックアップの暗号化・権限分離、削除時の扱いを決め、隔離環境への復元を実証してから運用開始する。復元の手順・担当者・実施記録を残す。ブラウザー内保存はバックアップとして扱わない。
