# 氏名・メール確認・管理者承認によるログイン

## 現在の状態

ログイン画面、確認コードの送信/検証、HTTPOnly Cookie、承認待ち、管理画面、サーバーでのアクセス判定、登録情報のDB権限制御を実装しています。**実際のSupabaseプロジェクト・メール送信元・Next.js公開サーバーは未接続で、実メールの送受信と本番ログインは未確認です。** アカウントの作成、外部サービスの契約、実スタッフへのメール送信は行っていません。

GitHub Pagesはサーバー認証を実行できないため、公開物をログイン準備画面だけに変更しました。社内機能のコード・名簿・実売上を含めず、URLの `#/daily` 等を変えても開きません。この画面からは確認メールを送信できません。サービス接続まで、初期管理者も含めて入れない状態です。

## 利用の流れ

1. 氏名・メールアドレスの両方を入力します。
2. メールに届いた6〜10桁の確認コードを入力します。入力だけで通る簡易ロックや、ブラウザーのログイン済みフラグは使いません。
3. 初回は `pending`（承認待ち）です。本人が自分の所属・役職・管理権限を決めることはできません。
4. 管理者が申請の氏名・メールを確認し、役職・店舗・権限を設定して承認します。
5. 承認済み本人のみが社内画面を開けます。登録済みの氏名と異なる場合・利用停止中・メール変更時は開けません。

役職は「総合責任者」「店長業務」「社員」「パートアルバイト」「他メンバー」。システム権限は従来の「一般スタッフ」「店舗管理者」「全社管理者」「システム管理者」と別管理です。承認済みの一般スタッフ・店舗管理者には店舗指定が必要です。全社管理者は一般スタッフ・店舗管理者を承認でき、高位管理権限の付与・管理者同士の変更はシステム管理者に限定しています。最後の有効な管理者を停止・降格する操作はDBで拒否します。

依頼者から預かった7名の氏名と確認済みメールは、リポジトリ外の登録準備ファイルにのみ保持しています。公開ページ・Git履歴・開発用データには含めません。メール未確認・所属未確認の方を勝手に登録・配属せず、登録待ちとして扱います。

## 接続手順（アカウントをまだお持ちでない場合）

### 1. Supabaseを作成する

管理者ご本人が [Supabase Dashboard](https://supabase.com/dashboard) へGoogle等でログインし、組織・プロジェクトを作成します。検証はFreeプランを候補とし、有料プランの申込は依頼者の確認後に行います。DBのパスワード・secret/service_roleキーをこのチャットやGitへ貼らないでください。

プロジェクトのSQL Editorで [登録テーブルと権限のSQL](../supabase/migrations/202610250001_membership.sql) を実行します。既存の業務テーブルやスタッフ情報を上書きするSQLではありません。このファイルは実プロジェクトでは未実行です。

Authenticationでメールログインを有効にし、メール確認を必須にします。**Magic Linkのメールテンプレートにはリンクだけでなく `{{ .Token }}` の数字コードを必ず含めます。** 本実装はコード入力方式で、リンクのコールバック方式ではありません。コードの期限は短く設定（例：10分）し、Auth側の送信・検証レート制限を有効にします。

メール本文例：

```html
<h2>WUTO-WURK ログイン確認</h2>
<p>確認コード：<strong>{{ .Token }}</strong></p>
<p>ポータルの確認コード欄に入力してください。心当たりがなければ入力しないでください。</p>
```

Supabase標準の送信機能には送信数や宛先の制限があります。全スタッフが使う前に、管理者所有のメール送信元・カスタムSMTPを設定し、全宛先へ届くことを確認する必要があります。スタッフをSupabaseの組織管理メンバーへ招待して制限を回避する運用にはしません。SMTPのパスワードはSupabase側で設定し、公開ソースには入れません。メール送信サービスの契約や費用の判断は依頼者が行います。

### 2. Next.jsを実行できる公開先へ接続する

GitHub Pagesには接続できません。既存のNode.jsサーバー、またはHTTPS対応のNode.jsホストが必要です。新規の検証先候補として [Render](https://dashboard.render.com/) のFree Web Service用 [render.yaml](../render.yaml) を用意しています。このファイルだけで契約・作成・デプロイは行われません。管理者が内容を確認し、GitHubリポジトリへの接続と作成を行います。

Renderならリポジトリ `yairorian-stack/wutowurk`、ブランチ `codex/growth-portal-finance` を指定します。ビルド `npm ci && npm run build`、起動 `npm run start -- --port $PORT`。サービスの公開URLが確定したら、次の3つをサーバー環境変数に設定します。

| 環境変数 | 内容 |
| --- | --- |
| `SUPABASE_URL` | 対象プロジェクトのHTTPS URL |
| `SUPABASE_PUBLISHABLE_KEY` | publishableキー、または従来のanonキー。secret/service_roleキーは禁止 |
| `PORTAL_ORIGIN` | そのNext.jsサービスのHTTPS URL。末尾パス・クエリなし |

値は `.env.example` を参考にサーバーの設定欄へ入力し、Gitには保存しません。Supabase AuthenticationのSite URL等にも実際の公開URLを設定します。通常のWeb画面・メール疎通を確認してから、スタッフへ新しいURLを案内します。まだこの新URLは発行されていません。

Freeホストの待機・再起動・制限や、認証サービスのプラン条件は作成画面で確認してください。常時稼働やバックアップ等の有料設定は自動で追加しません。Vercel等を選ぶ場合も会社用途に適合するプランと費用を確認します。

### 3. 初期管理者を確認・有効化する

管理者ご本人が新しいポータルで氏名・メールを入力し、実メールのコードで本人確認します。この段階では承認待ちです。

リポジトリ外に用意した初期管理者確認用SQLを、プロジェクト所有者がSQL Editorで確認・実行します。このSQLは、指定の管理者のメールが確認済みで、指定氏名の申請が存在し、まだ管理者がいない場合だけ全社管理者へ設定し、変更を監査記録へ残すものです。実名・メールを含むため、公開リポジトリには置いていません。**まだ実行していません。**

以後は初期管理者の「アカウント設定 → スタッフの登録・承認」から、本人確認済みの申請を承認します。店長業務の担当店舗は依頼者確認後に設定します。申告された名前が名簿にあるだけで自動承認しません。

## 保護の範囲

各社内ページとAPIで毎回Supabaseの `getUser()` を使って本人確認し、DBの最新の承認状態・権限を確認します。Cookieの中身やブラウザー保存値だけで許可しません。氏名・権限は登録DBから取得し、通常のログイン利用者には旧「権限プレビュー」を出しません。CookieはHTTPOnly、HTTPS時Secure、SameSite=Lax。変更APIは設定済みOriginとの一致を必須にし、入力サイズを制限します。

DBの登録情報はRLSで本人・承認済み管理者に限定し、一般利用者に直接のINSERT/UPDATE権限を与えません。申請RPCはメール確認済み本人を `pending/staff` にしか登録できず、承認RPCは管理権限・店舗指定・最後の管理者の保護・変更履歴をDB内でも検証します。

**今回DBへ移したのはアカウント登録情報だけです。売上・週次目標・シフト・評価の共有DB化は未実装です。** ログイン後も業務データは従来の試作品の機能で、保存するものはユーザーIDごとに端末内で分離します。旧ブラウザーの共通保存記録は消さず、新しいアカウントへ自動で紐付けません。必要なら所有者が確認してバックアップから読み込んでください。

同じ端末の開発者ツールや、以前ダウンロードした確認用HTML内の情報まで保護するものではありません。実業務の機密情報をスタッフ間で安全に共有するには、別途サーバー側の店舗別DB・監査・バックアップへ移行する必要があります。

## ローカル検証と再現

```sh
npm ci
npm run build:pages
npm run build:review
npm run lint
npm run typecheck
npm test
npm run test:auth
npm run test:e2e
```

`test:auth` は本物のNext.jsサーバーを使い、認証プロバイダーだけを127.0.0.1の試験サーバーへ差し替えます。本番に認証を無効化する設定や、誰でも入れるテスト用ルートは追加していません。実メールは送りません。出力先は `test-results-auth/` に分離しています。

従来の60画面テストは `out-review/` の架空プロトタイプをループバック専用サーバーで確認します。これはログインの安全性を証明するテストではなく、公開・デプロイしない回帰試験用です。Pages公開スクリプトは `out-review/` を使いません。

SQLはPGliteのPostgreSQLエンジンで、実際のRLS・GRANT・SECURITY DEFINER関数を実行して検証します。Supabase実環境のSMTP・OAuth設定・本番の運用権限は、接続後に別途確認します。

## 運用

利用停止は管理画面から実施します。次のサーバーリクエストから社内画面・管理APIを拒否します。すでに本人の端末に表示・保存された内容の回収はできません。

アカウント情報のバックアップ・復元は、プロジェクト所有者が非公開のDBバックアップを取得・管理し、復元試験と保管期限を決めてから実運用します。自動バックアップやSMTPに有料機能を使う場合は、事前に依頼者へ確認します。初期管理者を全員停止する運用は避け、復旧はプロジェクト所有者による監査付きSQL操作で行います。
