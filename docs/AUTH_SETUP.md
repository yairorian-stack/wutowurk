# メール6桁コードを追加し、Googleを予備として維持する移行

## 現状と安全な反映順序

所有者から、本番Node.jsホストの公開・Googleログインでの本人疎通・Google許可リストSQLの成功（1 / true / true）が報告されています。これらは再実行しません。以下は追加のメールOTP移行です。過去のSMTP送信エラーの原因・現在の実配信は未確認です。

1. 追加コードをpushします。Google経路は残し、新しいDB関数が未適用の場合だけ、既存のGoogle判定へ互換動作します。接続障害や許可拒否では代替判定へ進みません。
2. `202610260002_email_otp.sql` を1回適用します。許可リストの人数・アドレスを追加せず、同じ既存の許可リストに対して、確認済みメールOTPのセッションも認めます。旧 `portal_request_access` は再開しません。
3. Renderの非公開Environmentに `PORTAL_OTP_ALLOWED_EMAILS` を設定します。現在の許可リストと一致する所有者1名だけを指定するファイルをリポジトリ外に準備しています。送信前の制限に使うため、publishableキーで許可リストを匿名公開したり、Node.jsに高権限のservice_roleキーを追加したりしません。
4. SupabaseのEmail providerを有効にし、メール本文に `{{ .Token }}` を含め、OTPを6桁・期限10分に設定します。送信・検証のAuth側レート制限も有効にします。Gmail SMTPの資格情報はSupabase内だけで扱い、Render・チャット・Gitへ転記しません。
5. 所有者本人のアドレスで1回送信し、実メール受信・6桁コードによる本番ログイン・ログアウト後の未認証拒否を確認します。確認できるまではGoogleを外しません。外す場合は改めて依頼者に確認します。

過去のGoogleマイグレーションや初期テーブル作成SQLは再実行しません。実績売上を同時に反映する場合は、上記追加SQLと `202610260003_shared_sales.sql`、非公開の実データ登録を1回のトランザクションにまとめたファイルを使えます。結果は有効な試験アカウント数・OTP関数の準備・取込行数だけを表示し、アドレスや売上金額を結果に出しません。

## 送信濫用と列挙を防ぐ仕組み

メールアドレスだけではログインできません。アプリ内の6桁コード検証に加え、DBがSupabaseの署名済みセッションのotp認証記録・本人確認済みメール・有効な許可リスト・承認済みメンバーを確認します。氏名・役職・店舗は非公開の登録値から取得します。Googleの氏名入力は予備経路に残ります。

送信先はRenderの非公開リストに限定します。Authへの要求は `shouldCreateUser:false` とし、既存Authユーザーだけを対象にします。新規スタッフの追加時は、DB許可リスト、Render送信先リスト、既存Authアカウントの用意を所有者がそろえてから利用します。DBから取り消したアドレスがRenderに残っていても、DBのRLSと登録関数が社内閲覧を拒否します。送信先リストからも速やかに除いてください。

登録外・制限中・送信予定のアドレスで同じHTTP応答と同じ形の短期Cookieを返し、配信は応答後に行います。送信結果から登録状況を公開しません。失敗したコード検証も、宛先・コード・試行上限にかかわらず同じメッセージと最小の応答時間を使い、Auth呼び出しには時間制限を設けます。

単一サーバー内では宛先ごとに1分間隔・1時間5通、IP区分ごとに1時間10通、全体30通の上限を設けます。10分期限のHttpOnly/Secure/SameSite Cookieとサーバー内の不透明な試行IDを使い、1試行5回までの検証とします。再起動で試行状態は失われ、安全側に拒否します。これらのサーバー内制限は、再起動・複数台・Supabase APIへの直接呼び出しをまたぐ防御ではありません。共有の送信・検証制限はSupabaseにも必ず設定します。IPヘッダーはホストのプロキシ仕様に依存する補助制限です。

配信不能時のサーバーログは固定の一般的な警告だけです。宛先・コード・トークン・SMTP応答本文は出しません。GoogleのクライアントシークレットやGmailアプリパスワードは変更・取得していません。

## 運用の区別

今回のメールOTP・売上スナップショットは本番接続後の確認が必要です。ローカルのテスト成功は実メールの配信成功を意味しません。売上の共有読取以外の入力、シフト、評価の共有保存DBは別途未実装です。

## 予備Googleと公開先の維持

Google OAuthのWebクライアント、Supabase Google provider、本人のGoogleテストユーザーは所有者が設定済みです。少人数試験は所有者1名だけで、他のスタッフの追加は後に回します。Google providerを無効にしたり、OAuthクライアントを削除したりしません。メールidentityが追加されてもGoogle経路を維持し、他社OAuth identityによる曖昧な経路は引き続き拒否します。

Renderの本番Node.jsホストは所有者が作成済みと報告しています。既存の `SUPABASE_URL` と `SUPABASE_PUBLISHABLE_KEY` を維持し、originはRenderの `RENDER_EXTERNAL_URL` または明示的な `PORTAL_ORIGIN` を使います。Google client secretをNode.jsの環境変数へ移しません。Site URLとGoogle用の正確な `/auth/callback` 許可も残します。新しいメールコード方式はリンクのコールバックを必要としません。

GitHub Pagesは閉じた準備画面のままです。実績や名簿を静的HTMLに埋め込む公開方法へ戻しません。ブランチへのpush後、Renderの自動反映はホストの設定・デプロイ結果を確認してから完了と報告します。無料プランの休止・再起動があることを少人数で確認し、有料契約やカード登録は自動で行いません。

## 検証

`npm run lint`、`npm run typecheck`、`npm test`、`npm run build`、`node scripts/build-pages.mjs`、`npm run test:auth` を使います。DBはPostgreSQLエンジンによる実際のRLS/RPC/GRANTを検証し、ブラウザーはループバックの架空プロバイダーで検証します。実際のメール受信・Google同意・Renderの反映結果をこれらのローカル試験で代用しません。
