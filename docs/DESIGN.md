# WUTO-WURK Growth Portal — 試作品設計

2026-10-25追記：氏名・メール確認・管理者承認と登録DBの権限制御を実装した。外部サービスは未接続で公開Pagesは準備画面だけに閉じる。現在の認証設計・接続・制限は `docs/AUTH_SETUP.md` を正とし、以下は初期の業務プロトタイプ設計として保持する。

## 範囲と仮定

最初の目標は STEP 1・2。ホーム、ビジョン、週次目標を架空データで操作できる試作品とする。資料は承認済み原本が未提供のため、サンプル案内のみ。実在人物・就業規則は収録しない。外部契約・公開は行わない。

ブラウザー内保存は端末・ブラウザー単位。共有、バックアップ、認証、機密情報保護を提供しない。試作品に個人情報・社内機密を入力しない。権限プレビューは UI の確認用であり、安全なアクセス制御とは扱わない。実データ導入前に STEP 3 のサーバー実装が必須。

## データ構造

試作品は `src/lib/domain.ts` のスキーマを正とし、バージョン付きのローカルストレージに保存。店舗ごと・月曜開始の週ごとに目標最大3件。達成率 = 完了件数 / 全件数（保留も分母に含める）、0件は0%。先週の複製と未完了繰越は元IDを記録し、同一移行の二重実行を禁止。繰越は元記録を保持して新週に未着手で作成。期限は新週に同じ曜日で移す。履歴は前後の内容・日時・デモ実行者を保持する。

本番の PostgreSQL では以下を独立テーブルとする。

| テーブル                            | 主な列                                                                                                                    |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| stores                              | id, country_code, city, name, timezone                                                                                    |
| profiles                            | auth_user_id, display_name, position_title（役職名）, active                                                              |
| memberships                         | user_id, store_id, role（システム権限）                                                                                   |
| weekly_plans                        | id, store_id, week_start, week_end, meeting_at                                                                            |
| goals                               | id, weekly_plan_id, title, action, assignee_id, due_date, status, outcome, reflection, next_step, source_goal_id, version |
| vision_phases / vision_translations | 年、目標、行動、指標、移行条件、locale、公開状態                                                                          |
| documents / document_versions       | ストレージキー、版、更新日、公開状態、承認者、対象権限・店舗                                                              |
| audit_events                        | actor_id, entity_id, operation, before, after, created_at                                                                 |

目標3件制限はトランザクション内で親行をロックして検証。本番は楽観ロック version で競合を検出し、履歴は同一トランザクション内でサーバーから追記。週境界は店舗タイムゾーンで処理。将来の翻訳、国・都市、個人目標、商品開発は別テーブル・モジュールに分離する。

## 本番権限設計（STEP 3、未実装）

| -------------- | ------------------ | ---------- | -------------------------------------- |

認証は個人アカウント。JWT をサーバーで検証し、DB の memberships を正として店舗スコープを判定する。リクエストの role/store_id は信用しない。Supabase を採用する場合は PostgreSQL RLS とプライベートストレージを併用。資料は公開条件を照合した後に短時間の署名付きURLで配信する。未承認資料はスタッフに一切返さない。公開API・クライアントバンドルに機密データを含めない。給与・評価・面談の将来テーブルは本人と指定管理者だけに制限する。

## 本番への移行判断

認証提供元、ドメイン、料金プラン、初期管理者の本人確認・権限、個人情報の保持期間は依頼者の確認後に確定。公開は別途承認を得る。STEP 4 では3権限以上で API と RLS の直接リクエストを検証し、他店舗の読み取り・更新、権限昇格、未承認PDF、未認証アクセスを拒否することを確認する。

バックアップはDBの日次自動バックアップ＋資料ストレージの独立バックアップを予定。暗号化・アクセス制限、保持30日をたたき台とし、RPO 24時間・RTO 1営業日を依頼者と合意する。四半期ごとの隔離環境への復元訓練、操作履歴の保持期間、退職時の即時アクセス停止を運用手順に含める。現段階でこれらを実装済みとしない。
