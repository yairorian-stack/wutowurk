# 非公開の営業日報・本店出納帳の日次取込

## 現状と公開前の境界

コード・加算的DB migration・テスト・GitHub Actions workflowを準備する段階です。Googleサービスアカウント、GitHub secrets、実シートの初回dry run、実DB migrationの実行は別途必要です。コードをpushしても接続設定は完了しません。原本シートは変更しません。羽ノ浦出納帳は年度不整合のためこのリリースでは取得も登録もしません。

実数、シートID/URL、メール、鍵JSON、DB管理キーはこの文書・公開Git・ビルド成果物・Actions artifactへ置きません。原本レイアウトの説明のみで、セルの実配列はこの実行環境から未取得です。厳密なヘッダー検査を実装しているため、最初のdry runで実際の結合セル・年/店名の位置・空行・繰越行表現が適合するか確認する必要があります。失敗時に検査を外して通してはいけません。閲覧できる担当環境で、個人情報・金額をログに出さず構造を確認して解析を調整します。

## 無料の実行方式

`.github/workflows/sheets-sync.yml` は GitHub Actions の日次実行（UTC21:00＝日本時間翌06:00）と手動実行に対応します。実行時刻には遅延・実行漏れがあり得ます。Render Freeのスリープや有料cronには依存しません。Actionsの利用枠・アカウントの利用可否は設定時に確認し、課金を有効化しません。

**scheduleはリポジトリのデフォルトブランチにworkflowがある場合だけ動きます。** 現在の開発ブランチにpushしただけでは毎日実行されません。レビュー後にデフォルトブランチへ取り込むか、所有者が適切なデフォルトブランチを指定する必要があります。Renderの接続ブランチは既存設定を維持します。手動実行もGitHubの一覧にworkflowが出る状態にしてから対象ブランチを選びます。公開repoでは長期無活動でscheduleが停止する場合もあり、更新日時で監視します。

## 所有者による初回設定（秘密をチャットに貼らない）

1. 既存Google CloudプロジェクトでSheets APIを有効化し、取込専用サービスアカウントを作成。プロジェクトの編集者/所有者ロールは不要です。原本2ファイルだけをそのアカウントのメールへ「閲覧者」として共有します。リンクを一般公開しません。秘密鍵JSONはGitHubのsecret入力欄に直接登録し、チャットやリポジトリへ貼りません。
2. GitHub Environment `production-data-sync` を作り、次の4つをEnvironment secretsへ登録。Environmentで実行元をレビュー済みブランチだけに制限し、必要なら初回承認を設定します。

| Secret | 内容 |
|---|---|
| `SHEETS_SERVICE_ACCOUNT_JSON` | 専用Googleアカウントの秘密鍵JSON全文 |
| `SHEETS_SYNC_CONFIG` | 非公開で準備した原本ID・タブ名・範囲・月・ヘッダー行数・売上ブロック定義のJSON |
| `SUPABASE_SYNC_URL` | 現在のSupabaseプロジェクトURL |
| `SUPABASE_SERVICE_ROLE_KEY` | 同じプロジェクトの既存service_roleキー。ブラウザー用publishableキーとは別 |

service_roleは強い権限を持ちます。RenderやNEXT_PUBLIC変数へ追加しません。Actionsでの取込にだけ渡し、Actionsログに環境全体・HTTP原文・source rowsを出しません。workflowはPRやforkから実行しません。Googleへの要求スコープは`spreadsheets.readonly`だけ、token_uriは固定、redirectは拒否します。

3. workflowを手動実行し、**dry_run=true**で原本解析のみ検証。DBへは書きません。原本ヘッダーの年月・店名、売上列、入出金列、繰越残高を照合します。private configの`headerRows:4`は説明上の行5開始に基づく初期値であり、初回実データ検証が必須です。
4. 所有者がSupabase SQL Editorで `supabase/migrations/202610280001_sheets_sync.sql` を**1回だけ**実行。既存001〜003は再実行しません。DROPや旧データ削除はありません。
5. 再度手動実行、**dry_run=false**。本店・両店売上・羽ノ浦店長・未認証で画面を確認します。試験には本番の実ユーザーへ勝手にメールを送らず、所有者が自分でログインします。
6. 成功後にGitHub repository variable `SHEETS_SYNC_ENABLED=true`を登録。翌朝以降の実行を確認。GitHubのActions失敗通知を所有者が受け取る設定にします。自動メール/LINE送信先はこの変更で新設しません。

JSONは sales:{spreadsheetId,tab,range:"A1:AC400",blocks:[{store,column,year,months}]} と cash:{spreadsheetId,tab,range,store:"honten",year,month,headerRows}。columnは0始まり。初期売上ブロックはA/F/K/P/U/Zから4列ずつ、年2026、月[8,9]/[10,11]/[12,1]。本店出納帳の初期範囲はEF1:EN2000、2026年10月。羽ノ浦の未確認原本IDは設定に含めません。別の月へ移るときは確認済みの本店月ブロックにconfigを更新し、dry runを経て有効化します。未確認の月・列を自動推測しません。

## 保存・照合・失敗時

- 売上は`portal_sales_records`の(店舗,営業日)でupsert。旧snapshot全体から最新の各店舗日をseedし、旧テーブルは保持。日付の部分更新で過去は消えません。空欄はnullのままで、既存値の削除/0円への変換は行いません。月累計はDB取得後に日別実績から計算。元シートには累計列がないため「提供累計との照合済み」とは表示しません。
- 金額書式・実際の暦と曜日・年またぎ・店名・列ヘッダー・重複・未来の実績を検査。既存日別売上の訂正差額が10万円または旧値の50%の大きい方を超えると取込を止めます。正当な大幅訂正は所有者が照合し、別途レビューして反映します。変更された日から同月末までの提供累計前年比は無効化し、再計算/推定しません。
- 本店出納帳は月日空欄を直前の日付から継承し、(店舗,固定月ブロックID:原本行番号)をキーとします。原本の入金・出金・残高をそのまま保存。前月繰越行が必須で、全行の「前残高＋入金－出金＝残高」と既存前月末残高（あれば）を検査。売上総額とクレジット等控除がある原本はそのまま2行を表示し、別の現金売上行を自動生成しません。銀行への入金は原本の出金欄に従います。
- 元行番号はシートに挿入すると変わるため、毎回**対象月全体**を1トランザクションで置換公開します。旧行はinactiveとして保持、正常回の非公開payloadも監査用に保持。取込済み件数の減少や最終日の後退は停止し、消失・年度誤りを黙って反映しません。再実行は同じrun IDで重複せず、新しいrun IDでも同じ明細を二重加算しません。
- 解析エラーや残高不一致では売上・出納帳の両方を更新せず、前回値を維持。GitHub jobは失敗し、DBへ接続できる場合は固定コードの失敗履歴を記録。DBへ接続できない失敗は画面へ反映できないためGitHub通知と更新日時で確認します。
- UIに最終成功日時と最新実行結果、出納帳対象月、羽ノ浦年度確認待ちを表示します。原本の実査現金が未提供なので、計算残高と実査残高の過不足は未照合です。
- 新規表も既存`portal_sales_can_read`のRLSを使用。店長は自店のみ、全社管理者は両店、一般スタッフ・停止/未承認・未認証は不可。取得には本人の認証クライアントだけを使い、service_roleで画面の全店取得をしません。新取込RPCはservice_roleだけに許可。

## 運用の限界

最初の実シートdry run・実DB migration・定期実行・実績照合は秘密設定後に必要です。コードテストは架空値だけです。新しい年度の羽ノ浦出納帳はユーザーが原本を特定するまで有効化しません。元シート自体の新規記入やPOSからSheetsへの自動転記は対象外で、Sheetsに記入された確定値を取得します。
