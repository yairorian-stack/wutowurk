# 営業日報・店舗別出納帳の非公開日次取込

## 公開前の境界

コード・DB migration・テスト・GitHub Actions workflowを準備済みです。実Google Sheetのdry run、実DB migration・本取込・定期実行の成功は、所有者の秘密設定後に確認します。コードのpushだけでは自動取込は開始しません。原本は読み取り専用で変更しません。公開Git・ログ・artifact・fixturesに実数、原本ID/URL、個人情報、鍵JSON、DB管理キーを置きません。

羽ノ浦の正本は「39期目816　出納帳」です。「38期」のタブや「のコピー」は使用しません。先頭B:Iの壊れたブロックは取得禁止です。2026年10月のAD:AKだけを有効化し、8月L:Sと9月U:ABは原本の月・残高確認待ちとして無効化します。8月の数字を9月へ、9月の数字を10月へ読み替えません。

羽ノ浦は行3・範囲内列0の年、行5・範囲内列0の月、行4の8列見出しを厳密に検査します。行1に残る別年の表題は使いません。正本タブ名と確認済みsheetIdをSheets APIのメタデータでも照合し、コピーへ自動的に切り替えません。rangeはAD1:AK2000を指定できますが、実際の取得はメタデータの行数上限へ縮めます（1000行シートで範囲外エラーを起こさない）。上限まで値が詰まった場合は切捨てず停止します。

## 必要な所有者設定

1. 既存Google CloudプロジェクトでSheets APIと取込専用サービスアカウントを用意。プロジェクトの所有者/編集者ロールは不要。**営業日報、本店出納帳、羽ノ浦出納帳の3ファイル**だけを専用アカウントへ閲覧共有します。一般公開リンクにしません。
2. GitHub Environment `production-data-sync` に次の4つをsecretsとして直接登録。チャットやリポジトリへ貼りません。実行元をレビュー済みブランチに制限します。

| Secret | 内容 |
|---|---|
| SHEETS_SERVICE_ACCOUNT_JSON | 専用Googleサービスアカウントの鍵JSON |
| SHEETS_SYNC_CONFIG | 原本ID、正本タブ、範囲、店舗・年月・sourceId・セル位置・有効/無効を含む非公開JSON |
| SUPABASE_SYNC_URL | 現在のSupabaseプロジェクトURL |
| SUPABASE_SERVICE_ROLE_KEY | 同じSupabaseの既存service_roleキー |

service_roleは強い権限を持つため、Render/NEXT_PUBLIC変数/ブラウザーには渡しません。Actionsの取込でのみ使用します。Googleスコープはspreadsheets.readonlyのみ、token endpointは固定、HTTP redirectは拒否。PR/fork実行はありません。Actions依存をコミットSHAで固定し、npm ciはignore-scriptsを付けます。

3. 手動workflowを**dry_run=true**で実行。DBへは書きません。レイアウト・繰越行・残高式・営業日報の同日売上を照合します。セル配列自体はこの開発環境で取得できていないため、初回の実データ検証は必須です。エラー時に検査を外して通してはいけません。
4. Supabase SQL Editorで未適用の追加migrationを順番に**各1回だけ**実行：
   - `202610280001_sheets_sync.sql`（未適用の場合のみ）
   - `202610280002_cash_month_sources.sql`
   初期認証001〜売上003など適用済みmigrationは再実行しません。002は既存表・実績を保持し、両店対応と店舗/月/原本行キー、月別結果表、RPCを追加します。旧Honten一括RPCのservice_role実行許可は取り消し、新しい照合を迂回させません。
5. 手動で**dry_run=false**。全社、本店店長、羽ノ浦店長、未認証で画面を確認します。本人のログインは所有者が操作し、テストで実ユーザーへ勝手にメールを送りません。
6. 日次workflow専用のPR #2はmainへ反映済みです。所有者側でmainのcheckout固定SHAを、この修正を含む新しいコミットへ更新してください。大きいポータルPR #1はmergeしません。初回確認後にrepository variable `SHEETS_SYNC_ENABLED=true`を設定し、GitHubの失敗通知を所有者が受信する設定にします。

## 非公開config v3：39期通期の売上正本

[秘密値を含まない設定例](sheets-sync.example.json) を参照してください。例のspreadsheetIdとsheetIdはダミーで、cashSourcesは安全のため無効です。既存の非公開接続先IDへ置き換え、出納帳の有効/無効状態は確認済み設定を保持してください。本番secretsをこの開発作業では変更しません。

salesは正式な通期タブ「2店舗合計 日間売上と人時売上」を正本とし、format:"fiscal-year-vertical"、range:"L1:V400"、fiscalYearStart:2026、firstDataRow:3、lastDataRow:368、確認済みsheetIdを設定します。旧「[39]本店＋羽ノ浦」の横並びblocks設定は、この日次取込では使いません。L=日程、M/P=両店舗の日別売上、N/Q=月累計、U/V=店舗別労時です。8〜12月を期首年、1〜7月を翌年として、2026-08-01〜2027-07-31の全日付を検証します。月が変わるたびのコード変更は不要です。凍結行数から開始行を推測しません。

表示文字列(formattedValue)と実数値(effectiveValue)を1回のGridData応答から読み、表示上の通貨文字列を実入力と誤認しません。M/Pが数値の場合だけ店舗日を生成します。空欄/空文字は未入力で、累計・全社合計・比率などの式が0でも売上にしません。実数0は0円として保持します。未来の記入済み売上は拒否します。労時の空欄はnull、実数値は時間単位として分へ換算します。

原本全期の日付が重複なく順に揃うこと、暦/曜日、店舗別列の見出し、値の型、記入済み日の月累計を検証します。新規行の前年比O/Rはこの変更で書き込まず、従来の既存提供値保持/訂正時無効化を維持します。DBの既存店舗+営業日upsertを使うため**この通期対応に新しいmigrationは不要**です。先行migrationが未適用なら下記の手順が必要です。

cashSourcesは引き続き配列です。各要素には次を指定します。

- spreadsheetId、tab、range（列を絞ったA1形式）、store（honten/816）、year、month
- sourceId：月ブロックを識別する安定した名前。原本の行番号と組み合わせ、毎回同じ名前を使う
- enabled：確認待ちはfalse。falseのブロックはAPIで取得しない
- headerRows：取引解析より前の行数
- 任意のsheetId、yearCell:[1始まり行番号,0始まり範囲内列]、monthCell、labelsRow

羽ノ浦はyearCell:[3,0]、monthCell:[5,0]、labelsRow:4、headerRows:4。2026年10月には **openingValueRow:6** と **firstTransactionDate:"2026-10-01"** も必須です。8/9月はenabled:false、10月だけenabled:true。正本のsheetId一致も必須です。現リリースでは羽ノ浦の有効化は確認済み2026年10月AD:AKだけに制限しています。8/9月を修正後に有効化するには、所有者の原本確認を経てコード側の制限とDBのblocked状態を別途レビューして解除します。秘密設定だけを誤って変えて公開させません。本店の初期範囲は2026年10月EF:ENです。

## 羽ノ浦10月の分割繰越（明示設定のみ）

行5は月10・科目「先月繰り越し」で、日・曜・概要・入金・出金・残高は空欄。openingValueRowで指定した行6は月空欄・日1・曜は日本語1文字、科目/概要/出金は空欄、入金と残高が同額の開始残高です。指定行を探し直したり金額を推測したりせず、この組合せと違えばSOURCE_VALIDATION_FAILEDで停止します。出金0も空欄とは扱いません。

行6は開始残高の補助行として消費し、入金明細や売上として保存しません。補助行の曜日は取引日の曜日検証には使用せず、そこから取引日も作りません。最初の無日付明細（行7以降）のために、別途レビュー済みのfirstTransactionDateを非公開configへ明示します。以後の実明細の日付/曜日・残高式・営業日報との同日売上照合は従来どおり厳密に検証します。本店の同一行の繰越形式は変更しません。

## 独立した検証と公開

- 売上は店舗+営業日でupsert。月累計は日別から計算し、1日更新で過去は消えません。空欄は0円や削除に変換しません。大幅な既存値訂正、重複、未来日、不正な暦/曜日/列構造、異常な月累計は停止。変更日以降の提供累計前年比は無効化し、推定しません。
- 営業日報の取込は1トランザクション。出納帳は**店舗・月ごとに別トランザクション**で公開します。ある月の残高/日報売上が不一致でも、別店舗・別月の正常なデータと営業日報は更新可能です。
- 出納帳は月日空欄を前行の日付から継承。明示された繰越/開始残高を必須とし、最初の売上から開始残高を推測しません。「前残高+入金-出金=残高」を全行で検査。前月の登録済み末残高があれば繰越を照合します。
- 各明細日について科目「売上」の入金-出金合計が営業日報の同じ店舗・日付と一致することを、解析処理とDBの両方で検査。日報値が空欄/未登録なら一致と扱いません。不一致はその月だけ公開停止。クレジット等の控除は原本の出金行を保持し、別の現金売上を生成して二重計上しません。銀行預入も原本の出金欄に従います。
- DBキーは店舗+月+source row key。行挿入で番号が変わるため、対象月全体を置換公開。旧行はinactive、正常回payloadは閲覧不可の監査表へ保持します。同じrunの再実行も別runの再取込も二重計上しません。件数減少・最終日の後退・異常値は停止し手動確認します。
- 月単位失敗は前回の正常値とlast_success_atを保持し、月別警告を記録。最初からblockedの月は明細と開始残高をRLSでも非公開にし、警告だけ表示。例外ではその月の途中更新をロールバックします。
- UIは店舗・月別の取込結果、前回成功日時、入出金・残高を表示。10月正常なら羽ノ浦明細を表示し、8/9月は「原本の月・残高確認待ち（非公開）」を表示。実査現金の過不足は未照合です。
- RLSは既存portal_sales_can_readを使用。全社管理者は両店、店長は所属店、一般スタッフ・停止/未承認・未登録・未認証には渡しません。月別警告や繰越残高にも同じ制限。画面取得にservice_roleを使いません。

## 定期実行・通知・制約

GitHub ActionsはUTC21:00＝日本時間翌06:00に実行予定です。時刻の遅延/実行漏れがあり得るため更新日時を確認。Render Freeのスリープや有料cronに依存しません。利用枠・アカウント状態は設定時に確認し、課金を有効化しません。scheduleはmainにworkflowがある場合だけ動きます。現在は専用workflowがmain上で特定SHAをcheckoutする構成のため、開発ブランチへpushするだけでは実行対象は変わらず、固定SHAの更新が必要です。公開repoの長期無活動で停止する場合もあります。

失敗月がある場合は他の正常月を処理してからjobを失敗扱いにし、GitHub通知で管理者へ知らせます。DBへ接続できれば月別警告も記録しますが、DB自体に接続できない失敗は画面に記録できません。既知の無効月は警告として残し、毎日の通知を増やすためだけにjob失敗にはしません。新しい自動メール/LINE送信先は設けません。

この変更はSheetsへの記入やPOS→Sheets転記を自動化しません。新しい月・年度は原本の正しい範囲を確認して追加します。Google実データの初回dry run・DB反映・本番表示照合は未完了で、架空値のコードテストと区別します。
